Core Concept

Scaling

Inexperienced candidates tend to make two mistakes: (1) they leap to horizontal scaling to solve any performance problem, even when it's not necessary, and (2) they don't consider the implications of horizontal scaling on the rest of the system. When you encounter a scaling bottleneck, make sure you're not throwing machines at a poor design.

Work Distribution

The first challenge of horizontal scaling is getting the work to the right machine. This is often done via a load balancer, which will choose which node from a group to use for an incoming request.

Work distribution needs to try to keep load on the system as even as possible.

Data Distribution

You'll also need to consider how to distribute data across the system. For some systems, this implies keeping data in-memory on the node that's processing the request. More frequently, this implies keeping data in a database that's shared across all nodes.

You'll need to be prepared to discuss how you're going to keep your data Consistent.

Consistency

In many system design interviews, you'll be asked to discuss the consistency of your data. Consistency, at the highest level, pertains to how much your users can tolerate getting stale data. A strongly consistent system will ensure that, after the data is written, all subsequent reads will reflect that write. A weakly consistent or more commonly eventually consistent system will not make this guarantee, instead allowing for a period of time where the data is stale.

Locking

Locks happen at every scale of computer systems: there are locks in your operating system kernel, locks in your applications, locks in the database, and even distributed locks - hence they are a common topic in system design interviews. Locks are important for enforcing the correctness of our system but can be disastrous for performance.

Lock Granularity

Use fine-grained locks to minimize blocking. For example, lock only a user's profile, not the entire user table.

Lock Duration

Hold locks for the shortest time possible, only during the critical section.

Lock Bypass

Consider optimistic concurrency control for read-only or retryable operations. Use compare-and-swap when possible.

Optimistic control assumes low contention, which works for many systems. However, it's not suitable for all scenarios, like updating bank account balances.

Indexing

Indexing improves data retrieval efficiency. A basic method uses hash maps, allowing O(1) time access by key. Another approach uses sorted lists, enabling O(log n) time retrieval through binary search, common in databases.

Specialized Indexes

Specialized indexes solve specific problems:
• Geospatial indexes for location data (e.g., finding nearest restaurant)
• Vector databases for high-dimensional data (e.g., similar image search)
• Full-text indexes for text data (e.g., document search)

Mature databases like Postgres often support specialized index extensions (e.g., PostGIS for geospatial). Otherwise, maintain indexes externally.

ElasticSearch is recommended for secondary indexes, supporting full-text, geospatial, and vector indexes. It can be set up with Change Data Capture (CDC) to sync with databases, though this introduces potential latency and failure points.

It's very common for candidates to introduce ElasticSearch as a potential solution to their problem without understanding its limitations or explaining how it's used.

Communication Protocols

There are two categories of protocols to consider: internal and external. For internal communication in a typical microservice application—which covers over 90% of system design problems—either HTTP(S) or gRPC will suffice. Keep it simple. Externally, you'll need to consider how your clients will communicate with your system: who initiates the communication, what are the latency considerations, and how much data needs to be sent.

  • HTTP(s): Use HTTP(S) for APIs with simple request and responses.
  • SSE (Server Sent Events (SSE): An efficient method for server-to-client updates. Unlike long polling, SSE uses a single, long-lived HTTP connection to push data from server to client when available. This makes it ideal for scenarios requiring frequent, unidirectional updates. SSE is simpler than WebSockets, as it's designed solely for server-to-client communication. This simplicity allows for easier implementation and integration with existing HTTP infrastructure, including load balancers and firewalls, without special handling.
  • Long pulling: If you need to give your clients near-realtime updates, you'll need a way for the clients to receive updates from the server.
  • Websockets: WebSockets are for real-time, two-way communication between client and server. However, they present challenges in system design. Maintaining connections can strain load balancers, firewalls, and servers, especially with numerous open connections. A common solution is to use a message broker. This intermediary handles communication between clients and servers, while backend services interact with the broker. This approach simplifies connection management and improves scalability.

Security

Authentication / Authorization

Delegating authentication and authorization to an API Gateway or a dedicated service like Auth0 is an excellent way to avoid reinventing the wheel. Your interviewer might ask about the specifics of securing entities, but often it's sufficient to state, "My API Gateway will handle authentication and authorization."

Encryption

You'll want to cover both the data in transit (e.g. via protocol encryption) and the data at rest (e.g. via storage encryption). HTTPS is the SSL/TLS protocol that encrypts data in transit and is the standard for web traffic.

Data Protection

Monitoring

Once you've designed your system, some interviewers will ask you to discuss how you'll monitor it. The idea here is simple: candidates who understand monitoring are more likely to have experience with actual systems in production.

Infrastructure Monitoring

Infrastructure monitoring is the process of monitoring the health and performance of your infrastructure. This includes things like CPU usage, memory usage, disk usage, and network usage. This is often done with a tool like Datadog or New Relic.

Service-Level Monitoring

Service-level monitoring is the process of monitoring the health and performance of your services.
