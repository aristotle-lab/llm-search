System Design Learning Delivery Format

  1. write down the requirements for clarity:
    1. functional requirement: detailed features

      Functional requirements are your "Users/Clients should be able to..." statements. These are the core features of your system and should be the first thing you discuss with your interviewer. Then list out on the board.

    1. non functional: CAP theorem, environment constraints, scalability, latency, durability, security, fault tolerance, compliance

      Non-functional requirements are statements about the system qualities that are important to your users. These can be phrased as "The system should be able to..." or "The system should be..." statements.

    1. keep confirming with interviewer on the list
    1. ask do we need to estimate the capacity?
  1. write down the core entities (data model)

    Next you should take a moment to identify and list the core entities of you system. This helps you to define terms, understand the data central to your design, and gives you a foundation to build on.

  1. API or system interface

    Before you get into the high-level design, you'll want to define the contract between your system and its users. Oftentimes, especially for full product style interviews, this maps directly to the functional requirements you've already identified (but not always!).

    You have a quick decision to make here -- do you want to design a RESTful API or a GraphQL API?

    RESTful API: Uses HTTP verbs for CRUD operations on resources.

    GraphQL API: Allows clients to specify exact data to receive from server.

    Wire Protocol: Defines data format for websockets or raw TCP sockets.

    Prefer REST API. Use GraphQL for precise data fetching. For websockets, describe wire protocol.

  1. data flow

    For some backend systems, especially data-processing systems, it can be helpful to describe the high level sequence of actions or processes that the system performs on the inputs to produce the desired outputs. If your system doesn't involve a long sequence of actions, skip this!

  1. high level design

    Now that you have a clear understanding of the requirements, entities, and API of your system, you can start to design the high-level architecture. This consists of drawing boxes and arrows to represent the different components of your system and how they interact. Components are basic building blocks like servers, databases, caches, etc.

    Stay focused! It's incredibly common for candidates to start layering on complexity too early, resulting in them never arriving at a complete solution. Focus on a relatively simple design that meets the core functional requirements, and then layer on complexity to satisfy the non-functional requirements in your deep dives section. It's natural to identify areas where you can add complexity, like caches or message queues, while in the high-level design. We encourage you to note these areas with a simple verbal callout and written note, and then move on.

  1. deep dives
    1. ensuring it meets all of your non-functional requirements
    1. addressing edge cases
    1. dentifying and adressing issues and bottlenecks
    1. improving the design based on probes from your interviewer.
